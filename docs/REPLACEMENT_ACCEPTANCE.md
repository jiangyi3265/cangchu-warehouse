# 现有系统完整替换验收

目标：以若依 Vue 3、Java Spring Boot 和 MySQL 接替当前 Mintsoft 仓储业务。此目标持续有效，不能以某个模块完成、测试全绿或删除 Node 旧代码代替整体完成。代码现分别保存在 `cangchu-backend` 和 `cangchu-admin` 的 `main` 分支，验收文档保存在 `cangchu-warehouse` 的 `main` 分支。

2026-11-16（America/New_York）已按用户授权把本站切换到若依，并按确认使用空白业务库；旧演示库完整保留。此操作没有迁移客户 Mintsoft 业务，没有启用真实第三方请求。最新部署及交接见 [HANDOFF.md](HANDOFF.md) 和 [DEPLOYMENT.md](DEPLOYMENT.md)。后续客户业务切换仍按下表验收和用户授权执行。

依据：用户确认的完整若依迁移、原始 FULFILMENT 文档及只读调查记录、后续客户聊天中的平台/快递清单和按订单数阶梯计费要求。较早的“第三方先不做”已被“恢复开发，按正式替换推进”覆盖。原系统未实际验证的功能不能靠菜单或猜测宣称等价。

## 实施顺序与证据保存

1. 补齐仓内业务和财务闭环；每个模块包含 Java API、Vue 页面、权限、并发/失败保护和真实本地 MySQL/浏览器测试。
2. 迁入真实第三方适配和任务恢复，再用已有授权配置及实际账号验证。没有真实返回就不得把模拟面单、伪造单号或接口占位算作已接通。
3. 完成历史导入、数据对账、备份恢复和生产部署预演。之后再按已授权范围推进正式切换，保留回滚材料。
4. 任何开发顺序调整都不删除上表的剩余要求。原客户报价、历史账单、真实平台授权、快递服务和现场设备验证的缺口单独保留，不能用代码测试替代。

模块级证据与操作记录持续追加到 [迁移状态](RUOYI_MIGRATION.md)。私有测试账号、运行配置、原系统记录和测试截图保存在仓库外；公开仓库提交前扫描源码及历史中的明显敏感信息。是否可以整体替换，按本表逐项复核，不按菜单数量、代码行数或合成测试数量推算百分比。
